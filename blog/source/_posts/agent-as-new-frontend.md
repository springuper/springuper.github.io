State of Web Dev AI 2026 里有个数字挺反直觉：问到「你用 AI 生成哪一类代码」时，排第二的答案是前端组件，4434 次提及，仅次于工具函数，CSS 代码也有 3460 次。AI 其实早就在大量写界面了，只是我们很少用写界面的严谨程度来对待它。

这篇文章想回答一个问题：agent 算不算前端。我的答案是算，而且不只是打比方。你会看到一份十二条的对照表、三条可以直接复用的老经验、一份哪些技能能搬走哪些不用带的清单，还有一条我认为被传错的说法。

## 一、人机交互的第三次范式

几年前有人问我怎么看「前端已死」这个论调。我当时的回答是：

> 行业可能会有周期，但是我以为人机交互甚至交互这个根本性领域还会存在相当长时间。聚焦这个领域，而不限于单个技术栈，可能会是一个技术常青的做一番事业的有效路径。

当时写得顺手，现在回头看，这其实是个挺重的判断。如果把「前端」理解成浏览器里的那点东西，那它确实可能死；如果理解成人和机器之间的那一层，那它不但不会死，还会不断长出新东西。

我在一次分享里把这个观点展开过：命令行、图形界面、语音、手势、通知、终端里的字符网格，都该算在前端的范畴里。理由是它们回答同一个问题。一个不完美的系统，怎么把自己的状态变成人能理解和接受的呈现，同时接住人的意图。按这个划法，把自己锁死在某个终端介质里，大概是自我设限。

拿同一把尺子量 agent，它是什么就没什么悬念了：它当然是一种人机交互形态。真正值得追问的不是「算不算」，而是「它是哪一种」。

把交互史排一排，大致是这样：

| | 指令式 | 直接操作 | 意图式 |
|---|---|---|---|
| 起点 | 1960 年代终端 | 1983 年，Shneiderman | 2020 年代，agent |
| 人在做什么 | 学会机器的语言 | 操作对象本身 | 表达目标，审查结果 |
| 可见的对象 | 命令语法 | 对象与状态 | 决策与影响 |
| 出错怎么办 | 重新输入 | Undo，代价接近零 | 沙箱、审批、快照 |
| 设计目标 | 降低记忆负担 | 降低认知负担 | 在关键处提高认知负担 |

按这张表看，最要紧的是第三行。可见的对象从「对象」挪到了「决策」，后面两行就跟着变了。GUI 敢让人随便点，是因为 undo 让错误接近免费。**agent 的错误不免费，删掉就是删掉，所以它必须拿别的东西兜底，那就是沙箱和审批。** 这句话先放在这儿，第四节还会回来。

## 二、领地和造法是两个问题

上面这套划法回答的是「这属于谁的领地」。它其实还算不上工程答案，因为说不出明天该做什么。要把它变成能动手的东西，得回答第二个问题：这类程序到底由什么构成。

我习惯用六个要素来定义前端应用，它们跟技术栈无关：

1. 跑在一个自己无法控制的运行时里
2. 持有状态，并在状态变化时重新呈现
3. 通过协议与远端通信
4. 运行在一个能力受限的沙箱里
5. 面向一个会给出不确定输入的人类
6. 因此必须容错、降级、可取消

这六条不专属于前端。但凑在一起，刻画的的确是一类程序。浏览器是这类程序最成功的实例，而它 1995 年的时候，只是个文档查看器。

## 三、六个要素，逐条对照

把 agent harness 放到这六条前面比一比：

| 前端应用 | Agent | 同构点 |
|---|---|---|
| 浏览器 / Node 运行时 | Harness | 你不控制它，只能适配它的约定 |
| DOM / 虚拟 DOM | 上下文窗口 | 都是要被管理的资源，不是数据本身 |
| 组件树 + props | 提示词 + 工具定义 | 声明意图，运行时去执行 |
| 状态管理 | 上下文管理与压缩 | 有容量、要淘汰、要保关键信息 |
| 事件循环 | agent loop | 回合制、单线程、等外部结果 |
| 内存 GC | 上下文压缩 compaction | 预算有限，必须主动回收，而且有损 |
| tree-shaking | 上下文裁剪与检索 | 只把必要的带进来 |
| API 契约 / TS 类型 | 工具 JSON Schema | 契约写错，调用必错 |
| CORS / 相机麦克风授权 | 工具审批 / 沙箱策略 | 能力沙箱加用户中介授权 |
| XSS | 提示词注入 | 不可信内容进入执行路径 |
| 错误边界 | 重试、回退、交还人类 | 失败是常态，不是异常 |
| AbortController | 停止按钮 | 长任务必须可取消 |
| 单元测试 / E2E | Evals | 范式变了，验证手段跟着变 |
| DevTools | trace / 可观测性 | 没有观测就没有调试 |

这张表大部分格子其实一眼就懂。但有三条不是类比上的凑巧，是问题本身就一样，值得单独说。

## 四、三条不是巧合的同构

### 4.1 上下文窗口就是内存

内存有限，所以要分配、要回收、要处理碎片。上下文窗口一模一样。

不妨把它当成一次 GC。**而且是一次有损的 GC。** 垃圾回收至少还有个客观标准，没人引用了就是垃圾；压缩没有这个标准。把哪几轮对话揉成一句摘要、保留哪个文件的内容、丢掉哪次失败的尝试，全是策略问题。

这也是我读 Pi 的提交记录时大概最有感触的一处细节：它在动手写压缩机制之前，先写了一份研究文档。它不是先写代码，是先想清楚什么该记得。

顺着内存这条线，几个老问题会立刻变得面熟。

lost in the middle 说的是模型对上下文中间的信息最不敏感。当成一个可见性问题更好理解，重要信息没被渲染进视野。上下文裁剪像 tree-shaking，判断用不到就删，和打包器判断代码没被引用是同一件事。还有一条容易被忽略：真正决定架构的是预算，不是窗口标称多大。

开发者自己的体感也在这条线上。同一份调查里问「最希望 AI 补上什么能力」，长期记忆排第二，占 16.0%，仅次于真实性的 17.3%；大代码库支持 6.2%，运行时行为感知 8.3%。至于痛点那一栏，缺上下文排第三，占 14.2%，前面是幻觉和生成代码质量差。这些选项拼起来说的是同一句话：它记不住，也看不到足够多的东西。

### 4.2 工具调用就是 API 契约

一个有工具能力的 agent，本质上是在调用一批它看不见实现的接口。描述这些接口的东西是一份 JSON Schema。

这就是 propTypes，是 TypeScript 类型声明，是 OpenAPI 文档。它承担的责任完全一样：在调用发生之前把契约说清楚。

这里有个很实际的推论。**工具描述写得烂，等于接口设计得烂。** 参数名含糊、边界条件不写、错误返回不说清楚，模型就只能猜。它猜错的方式和人类工程师猜错的方式几乎一样，都是拿着一个看着合理的参数去调用，然后在一堆无关的报错里找线索。

差别有多大，看下面这个查询参数（示例，非某家真实工具的定义）：

| 写法 | 参数的 description |
|---|---|
| 差的 | 无 |
| 好的 | 搜索关键词。支持 AND / OR / NOT 布尔语法，不支持正则。空字符串会返回全部结果。 |

第二版多花了几十个 token，换来三件事说清楚：语法边界、不支持什么、边界情况的行为。这三件事正好是人类工程师写 API 文档时会写的东西。所以写工具描述不是「提示词技巧」，是接口设计，用的是同一套手艺。

那 19.9% 的「生成代码质量差」里，有相当一部分来源在这里。不是模型不会写代码，是它不知道你这个工具要什么。反过来，把工具描述当成接口文档来写，做的是同一件老工作。

再往上走一层，MCP 的位置也清楚了。它相当于工具世界的 HTTP，把「怎么描述和发现一个工具」标准化，让工具能跨 harness 复用。前端对这个套路很熟，我们就是靠一个协议把后端能力变成浏览器能用的东西。

### 4.3 沙箱就是浏览器的安全模型

这一条我认为最深，也最容易被当成顺口一说。

浏览器为什么要有同源策略、要有权限弹窗？因为它的核心矛盾是：不可信的内容会进入一条能操作真实资源的执行路径。页面里的一段第三方脚本不该读你的摄像头，也不该读另一个站点的 cookie。

现在把「第三方脚本」换成一段从网页、文件或工具返回里读到的文字，把「读摄像头」换成「删掉这个目录」，这就是提示词注入。

它们不是像，是同一类漏洞：不可信内容影响了一个有权限的执行者。所以浏览器过去三十年踩过的坑，几乎都能搬过来。

光靠过滤危险字符其实永远不够。当年防 XSS 的转义方案就是这么被打败的。**真正的解法是能力最小化，不是提高警惕。**

还有一条更值得做 harness 的人抄走：用户会用点「同意」来结束一切需要思考的对话，所以浏览器的方向从来不是问得更频繁，是让安全的默认值变得不必问。工具审批如果做成每次弹窗，结果不是更安全，是用户开始无脑点同意，这和当年的权限弹窗是同一个失败模式。

不妨回到第一节那句先放着的话。**沙箱不是 agent 的一个功能，而是它丢掉可逆性之后必须付的代价。** GUI 靠 undo 兜底，agent 靠沙箱兜底，两者在架构里的位置是一样的。

## 五、这条路的尽头

回头看浏览器怎么从文档查看器变成应用平台，靠的是三件事。状态，也就是 JS 加 DOM，页面第一次能记住东西。协议，也就是 XHR 和 fetch，页面第一次能带着数据自己更新。能力，也就是权限模型，页面终于能碰摄像头、文件和通知，还不至于出事。

把这三件事的 agent 版本排出来：状态是会话树和上下文管理，协议是 MCP，能力是工具审批和沙箱。已经全在了。

那接下来会缺什么？我猜缺的全是前端已经有的东西。

- 组件化。现在提示词是一大坨字符串，输出是一条线性文本流，可组合、带参数和状态的交互单元迟早会出现。
- 布局。同样是输出，什么该折叠、什么该突出、什么该并排对比，是布局决策。这件事现在被丢给了「让模型自己说清楚」。
- 状态管理。会话树已经有人做了，Pi 的原地分支就是个好例子，下一步是跨会话的持久状态。
- 设计系统。agent 的输出风格需要一致性约束，否则每次交互都从零开始。
- DevTools。没有观测就没有调试，这一条前端在 2010 年代就吃过教训。

这一串预测如果成立，那结论就有点意思了：**缺口全在「怎么让人看见」这件事上。** 模型能力的进步不解决它，因为这是呈现和交互的问题，不是推理的问题。

## 六、顺带纠偏：窗口开到一百万，就不用管上下文了？

这是我最近听到最多的一句。既然窗口都到一百万 token 了，上下文管理是不是可以不做了。

按 4.1 那条内存的线看，这个说法站不住。窗口变大相当于内存变便宜，内存变便宜从来没有让 GC 消失过。何况中间信息不敏感的问题不随窗口增长而缓解，反而更明显，东西越多越容易淹。

数据其实也不支持。如果窗口够大就没事，那「长期记忆」不会以 16.0% 排在最想要能力的第二位，「缺上下文」也不会以 14.2% 稳居痛点第三。

窗口解决的是容量，压缩解决的是预算和取舍。这的确是两件事，别混。

## 七、哪些能力能搬过去

老实说，这才是「前端已死」这个话题最实在的答案。

可以直接搬的：状态管理、信息层级与布局、感知性能、渐进披露、错误恢复与降级、授权的交互设计。

感知性能那一条大概最直观。流式输出就是骨架屏，用户等的不是结果，是「它在动」这件事。渐进披露也一样，agent 现在把一切一股脑倒在屏幕上，好的界面会分层：先摘要，再展开，最后才是细节。授权的交互设计则直接对应 4.3 那个失败模式，什么时候该问、问几次、默认给什么，前端的经验都是现成的。

不用带的：DOM 和 BOM 的 API、CSS 的具体属性、某个框架的 API、浏览器兼容性矩阵。

**你积累的不是浏览器知识，是怎么让一个人和一个不完美的系统共处的经验。** 这句话我觉得比任何一条具体技能都值钱，也是我对「前端已死」最正式的回答。

## 八、这个类比会在哪里失效

类比的价值在于复用解法，不在于证明两者相等。有几处它一定会断，我认为必须写出来。

**第一，前端的渲染是确定性的，agent 不是。** 同一个状态、同一份 props，React 一定给你同一棵树；同样的上下文、同样的工具，agent 可能给你完全不同的结果。前端那套可预测性的保证，纯函数、幂等、可重放，agent 一个都没有。第三节那张表右列的机制，都建立在一个前端有、agent 没有的地基上。

**第二，坏结果的代价不同。** 前端出 bug，最坏是体验下降、白屏、用户骂两句；agent 出 bug，是它删了一个不该删的目录、发了一封不该发的邮件。这不是程度差异，是性质差异。所以三条同构里沙箱那一条最重要，也是唯一一条不能「以后再补」的。

**第三，两边的用户要做的事相反。** 前端的用户在用界面，设计目标是降低认知负担，让他不用想；agent 的用户在审查决策，设计目标是在关键的地方提高认知负担，让他必须看见。把前端的顺滑直接搬到审批界面上，就是把人推向无脑点同意。

第一点倒是有个更硬的旁证。Simon Willison 讲提示词注入讲了好几年，他的判断一直是这个问题没有被解决，而且恐怕不容易被解决。他给出的危险条件是三件事同时成立：能碰到私有数据、会读到不可信内容、有办法把数据送出去。三件事凑齐，防护就很难做。

这其实还是浏览器的老命题换了张脸。当年浏览器也没有靠过滤解决 XSS，是靠把能力管起来。所以我在 4.3 说的不是比喻，是同一个解法。

## 结语

把全文收一下，方便回看：

| 问题 | 我的答案 |
|---|---|
| agent 算前端吗 | 算。按「人和机器之间那一层」来划，它是人机交互的第三种范式 |
| 凭什么这么说 | 六个结构要素逐条命中，其中三条是问题相同，而非表面相似 |
| 最要紧的一条同构 | 沙箱。它站在 GUI 里 undo 的位置，可逆性只是换了载体 |
| 最实用的结论 | 状态管理、信息层级、感知性能、错误恢复这些经验可以整包搬走 |
| 什么时候不成立 | 渲染不确定、坏结果代价高、两边用户要做的事相反 |

前端这二十年真正沉淀下来的，不是某个框架的 API，是一整套经验：当不确定的输入、受限的运行时和真实的人类这三件事凑到一起时，程序该怎么设计。组件怎么切、状态放哪、失败怎么降级、什么时候必须让人介入，这些答案不会因为技术栈换代而失效。

agent 把这三件事又凑了一次。所以我不觉得它是前端的替代品。**它是前端的下一个渲染目标。**
