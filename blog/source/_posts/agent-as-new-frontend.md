## 一、人机交互的第三次范式

几年前有人问我怎么看「前端已死」这个论调。我当时的回答是：

> 行业可能会有周期，但是我以为人机交互甚至交互这个根本性领域还会存在相当长时间。聚焦这个领域，而不限于单个技术栈，可能会是一个技术常青的做一番事业的有效路径。

当时写得其实挺顺手，现在回头看，这是个挺重的判断。如果把「前端」理解成浏览器里的那点东西，那它确实可能死；如果理解成人和机器之间的那一层，那它不但不会死，还会不断长出新东西。

我在一次分享里把这个观点展开过：命令行、图形界面、语音、手势、通知、终端里的字符网格，都该算在前端的范畴里。

理由是它们回答同一个问题。一个不完美的系统，怎么把自己的状态变成人能理解和接受的呈现，同时接住人的意图。按这个划法，把自己锁死在某个终端介质里，大概是自我设限。

拿同一把尺子量 agent，它是什么就没什么悬念了：它当然是一种人机交互形态。真正值得追问的不是「算不算」，而是「它是哪一种」。

把交互史排一排，大致是这样（Shneiderman 的直接操作理论发表于 1983 年，其余时间点为本文归纳）：

| | 指令式 | 直接操作 | 意图式 |
|---|---|---|---|
| 起点 | 1960 年代终端 | 1983 年，Shneiderman | 2020 年代，agent |
| 人在做什么 | 学会机器的语言 | 操作对象本身 | 表达目标，审查结果 |
| 可见的对象 | 命令语法 | 对象与状态 | 决策与影响 |
| 出错怎么办 | 重新输入 | Undo，代价接近零 | 沙箱、审批、快照 |
| 设计目标 | 降低记忆负担 | 降低认知负担 | 在关键处提高认知负担 |

按这张表看，最要紧的是第三行。可见的对象从「对象」挪到了「决策」，后面两行就跟着变了。GUI 敢让人随便点，是因为 undo 让错误接近免费。**agent 的错误不免费，删掉就是删掉，所以它必须拿别的东西兜底。** 兜底的东西是什么，第九节再回来说。

## 二、领地和造法是两个问题

上面这套划法回答的是「这属于谁的领地」。它实话说还算不上工程答案，因为说不出明天该做什么。要把它变成能动手的东西，得回答第二个问题：这类程序到底由什么构成。

我习惯用六个要素来定义前端应用，它们跟技术栈无关：

1. 跑在一个自己无法控制的运行时里
2. 持有状态，并在状态变化时重新呈现
3. 通过协议与远端通信
4. 运行在一个能力受限的沙箱里
5. 面向一个会给出不确定输入的人类
6. 因此必须容错、降级、可取消

这六条不专属于前端，但凑在一起，刻画的的确是一类程序。浏览器是这类程序最成功的实例，而它 1995 年的时候，只是个文档查看器。

## 四、三条不是巧合的同构

这一节引用的代码全部来自一个公开教学仓库 [build-your-claude-code-from-scratch](https://github.com/woodx9/build-your-claude-code-from-scratch)。它的做法是从零手写一个 Claude Code，一章一个能力，正好覆盖我要说的三件事：工具调用（chapter1）、agent 循环（chapter2）、历史与上下文控制（chapter4、chapter5）。选它是因为它足够小，小到能把机制看穿；也因为它够完整，不是一个玩具片段。

先交代一句：它其实是一个教学实现，定位是讲清楚原理，不是拿去上生产。下面的批评都冲着"这类结构容易犯什么错"，不是冲着作者。

### 4.1 上下文窗口就是内存

内存有限，所以要分配、要回收、要处理碎片。上下文窗口一模一样。

`chapter5_smart_context/src/core/history/history_manager.py` 里，触发回收的条件是一行很直白的算术：

```python
def _requires_compression(self) -> bool:
    if self._compress_threshold and self.history_token_usage:
        current_usage = self.history_token_usage[-1]
        return current_usage.total_tokens > self._compress_threshold * self._model_max_tokens
    return False
```

默认 `compress_threshold` 是 0.8。也就是说，用到窗口的 80% 就开始回收。这就是 GC 的触发阈值，只不过名字倒是叫 compression。

那它回收掉什么？这的确是我最想亲手看一眼的地方，所以我把这段逻辑真的跑了一遍。

```
压缩前：消息数 = 8
      角色序列 = system, user, assistant, tool, assistant, tool, assistant, user
      total_tokens=4000 时占用 97.7%，触发压缩

压缩后：消息数 = 3
      system   | You are a helpful assistant.
      user     | [Previous conversation history has been compressed to save context window space]
      user     | 顺便把 lint 也修了
```

8 条变成 3 条，中间那 5 条 assistant 和 tool 消息全部消失。消失的东西里有什么？有"我先看一下测试文件"、"找到问题了，在 src/parser.ts 第 42 行"、"应用补丁完成"。也就是说，**这一轮任务的过程记录被整段丢掉了，换来的只是一句固定的占位文本，没有任何摘要。**

这大概就是"有损"两个字的实际含义。垃圾回收至少还有个客观标准，没人引用了就是垃圾。压缩没有这个标准，丢什么全看策略写在哪一行。

也正因为没有标准，这类代码必须靠不变量来守。同一个文件里有一句注释，写得很清楚：

```python
# mustn't crop the latest user input message
```

实现里也确实在守它：先倒着找出最新一条 user 消息的下标，再用它算出两个方向各自允许裁多少。我把四种组合都跑了一遍：

| 操作 | 返回 | 结果 |
|---|---|---|
| `crop TOP 3` | Crop message successful | 8 条剩 6 条 |
| `crop BOTTOM 1` | Cannot crop: can't crop the latest user message | 保持不变 |
| `crop BOTTOM 2` | Cannot crop: can't crop the latest user message | 保持不变 |

BOTTOM 方向守住了。有意思的是 TOP 方向：按参数说明，`crop_amount` 是"要移除的消息条数"，但裁 3 条实际只少了 2 条。原因在这一行。裁剪结果里把 system 消息又拼了回去，而它们本来就在被裁掉的前缀里：

```python
system_messages = [msg for msg in current_messages if msg['role'] == Role.SYSTEM]
cropped_messages = system_messages + current_messages[crop_amount:]
```

我其实没去提 issue，也没法确定这是笔误还是有意为之，所以大概只能按"未验证"记着。但它恰好说明了一件事：**有损回收的全部危险性集中在这类算术里。** 它不会报错，不会崩，只是安静地少留一条或多留一条。前端做列表 diff 时踩过一模一样的坑。

### 4.2 工具调用就是 API 契约

一个有工具能力的 agent，本质上是在调用一批它看不见实现的接口。描述这些接口的东西是一份 JSON Schema。这就是 propTypes，是 TypeScript 类型声明，是 OpenAPI 文档，责任完全一样：在调用发生之前把契约说清楚。

这个仓库的 chapter1 给了两份对照实现，同一件事两种写法，放一起看特别清楚。

第一份是原生的函数调用：工具用 JSON Schema 声明，模型返回结构化的 `tool_calls`，宿主直接 `json.loads` 拿参数。

```python
tools = [{
    "type": "function",
    "function": {
        "name": "search_gutenberg_books",
        "description": "Search for books in the Project Gutenberg library",
        "parameters": {
            "type": "object",
            "properties": {
                "search_terms": {
                    "type": "array",
                    "items": {"type": "string"},
                    "description": "List of search terms to find books"
                }
            },
            "required": ["search_terms"]
        }
    }
}]
```

第二份把"契约"写成了提示词里的一段示例文本，让模型自己吐 XML，宿主再用正则去捞：

```python
xml_match = re.search(r"<search_gutenberg_books>[\s\S]*?</search_gutenberg_books>", model_text)
if not xml_match:
    raise ValueError("未找到 <search_gutenberg_books> 标签")
```

差别在哪？第一份里，参数名和类型是运行时校验的；第二份里，契约是一段自然语言，而校验等于一句 `raise ValueError`。第一份加第二个工具是往数组里再加一项；第二份加第二个工具，得再写一个正则，而且标签名硬编码在里面。

**契约由谁保证，决定了错误在什么时候暴露。** 这不是提示词技巧，而是接口设计，和写 REST 接口时纠结参数该不该必填是同一件事。

契约的分量有多大，老实说我也没想到，所以专门量了一下。这个实现一共两个工具，我把它们的 `json_schema()` 序列化后统计字符数：

| 项 | 字符数 |
|---|---|
| `cmd_runner` 的完整 schema | 7485 |
| 其中 `description` 说明文字 | 6852 |
| `smart_context_cropper` 的完整 schema | 3668 |
| 其中 `description` 说明文字 | 2745 |
| 两个工具合计 | 11153 |
| 用户任务原文「修复这个仓库里的 bug，让 npm test 全部通过」 | 28 |

**工具定义是用户任务的 398 倍。** 这个比例不一定普适，毕竟示例里的任务特别短，但方向是对的：你写的那段工具说明，占的是和用户对话同一条预算。它不是文档，它是每次请求都要重新付一遍的上下文。

顺着看还有一处细节，其实挺典型。chapter2 的循环里有这么一段：

```python
try:
    args = json.loads(tool_call.function.arguments)
except json.JSONDecodeError as e:
    self.messages.append({"role": "tool",
                          "name": tool_call.function.name,
                          "content": "tool call failed due to JSONDecodeError"})
    continue
```

参数解析失败时，它没有崩，而是把一句错误说明作为工具结果回灌给模型，让模型下轮自己改。**失败被当成数据，而不是异常。** 这就是错误边界，只是错误本身也变成了上下文里的一条消息。前端写错误边界时也是这个取舍：是抛出去让上层接，还是渲染成一个能继续操作的降级界面。

再往上走一层，MCP 的位置也清楚了。这个仓库的 chapter8 专门写了一个 MCP 客户端。MCP 相当于工具世界的 HTTP，把「怎么描述和发现一个工具」标准化，让工具能跨 harness 复用。前端对这个套路很熟，我们就是靠一个协议把后端能力变成浏览器能用的东西。

### 4.3 沙箱就是浏览器的安全模型

这一条我倒是认为最深，也最容易被当成顺口一说。

浏览器为什么要有同源策略、要有权限弹窗？因为它的核心矛盾是：不可信的内容会进入一条能操作真实资源的执行路径。页面里的一段第三方脚本不该读你的摄像头，也不该读另一个站点的 cookie。

把「第三方脚本」换成一段从网页或工具返回里读到的文字，把「读摄像头」换成「删掉这个目录」，这就是提示词注入。

先看这个仓库里，「沙箱」长什么样。执行命令的工具叫 `cmd_runner`，它的实现是这一行：

```python
result = subprocess.run(command, shell=True, capture_output=True, text=True, timeout=30)
```

`shell=True`，没有任何限制。那"安全"写在哪？写在工具说明里，写成了给模型看的行为规范：

```
1. Security Check:
   - Always check if the command is potentially dangerous (e.g., rm, sudo, chmod 777, format, del, etc.)
   - If the command is dangerous or could cause system damage/data loss, you MUST set need_user_approve=true
```

这段说明的确有 6852 字符，占了整个 schema 的九成。也就是说，**这个工具的安全策略，是一篇给模型读的作文。**

更值得琢磨的是审批本身。`need_user_approve` 不是宿主强加的门，它是工具的一个参数，由模型自己填：

```python
"need_user_approve": {
    "type": "boolean",
    "description": "Whether the crop messages action requires explicit user approval before execution",
    "default": True
}
```

宿主读它的时候是这样：

```python
need_user_approve = args.get('need_user_approve', False)
```

**默认值是 False。** 模型不主动要求审批，就没有审批。整条链路上没有任何东西在模型判断失误时兜底。

这正是浏览器三十年前学到的教训。当年防 XSS 靠转义和过滤危险字符，被打败了；沙箱和同源策略才是解法。**边界不是写在说明里的规矩，而是宿主画出来的线。** 上面这套结构，等于把边界交给了模型，而模型正是那个会读到不可信内容、可能被注入的一方。

Simon Willison 讲提示词注入讲了好几年，他的判断一直是这个问题没有被解决，而且恐怕不容易被解决。他给出的危险条件是三件事同时成立：能碰到私有数据、会读到不可信内容、有办法把数据送出去。三件事凑齐，防护就很难做。

上面这个例子恰好三件都占：能读文件、会读到命令输出、能通过网络发出去。

那正确的做法是什么？回到第一节那句话。GUI 靠 undo 兜底，agent 丢掉 undo 之后，兜底的东西只能是边界：能力最小化、默认拒绝、把危险操作放到进程外。前作里 Pi 的选择更极端，它干脆不做权限弹窗，理由是进程内的半吊子沙箱容易被误当成真正的安全边界，隔离请到操作系统或容器那一层去画。

两种做法倒是针锋相对（一个把策略写进提示词，一个把边界推到进程外），但立在同一个前提上：**信任不该放在模型这一侧。**

## 五、这条路的尽头

不妨回头看浏览器怎么从文档查看器变成应用平台，靠的是三件事。状态，也就是 JS 加 DOM，页面第一次能记住东西。协议，也就是 XHR 和 fetch，页面第一次能带着数据自己更新。能力，也就是权限模型，页面终于能碰摄像头、文件和通知，还不至于出事。

把这三件事的 agent 版本排出来：状态是会话树和上下文管理，协议是 MCP，能力是工具审批和沙箱。已经全在了。

那接下来会缺什么？我猜缺的全是前端已经有的东西。

- 组件化。现在提示词是一大坨字符串，输出是一条线性文本流，可组合、带参数和状态的交互单元迟早会出现。
- 布局。同样是输出，什么该折叠、什么该突出、什么该并排对比，是布局决策。这件事现在被丢给了「让模型自己说清楚」。
- 状态管理。会话树已经有人做了，Pi 的原地分支就是个好例子，下一步是跨会话的持久状态。
- 设计系统。agent 的输出风格需要一致性约束，否则每次交互都从零开始。
- DevTools。没有观测就没有调试，这一条前端在 2010 年代就吃过教训。

这一串预测如果成立，结论就有点意思了：**缺口全在「怎么让人看见」这件事上。** 模型能力的进步不解决它，因为这是呈现和交互的问题，不是推理的问题。

## 六、顺带纠偏：窗口开到一百万，就不用管上下文了？

这是我最近听到最多的一句。既然窗口都到一百万 token 了，上下文管理是不是可以不做了。

按 4.1 那段代码看，这个说法站不住。窗口变大无非相当于内存变便宜，内存变便宜从来没有让 GC 消失过。何况中间信息不敏感的问题不随窗口增长而缓解，反而更明显，东西越多越容易淹。

数据也不支持。同一份调查里问「最希望 AI 补上什么能力」，长期记忆排第二，占 16.0%，仅次于真实性的 17.3%；大代码库支持 6.2%，运行时行为感知 8.3%。至于痛点那一栏，缺上下文排第三，占 14.2%，前面是幻觉和生成代码质量差。这些选项拼起来说的是同一句话：它记不住，也看不到足够多的东西。

窗口解决的是容量，压缩解决的是预算和取舍。这的确是两件事，别混。

## 七、哪些能力能搬过去

老实说，这才是「前端已死」这个话题最实在的答案。

可以直接搬的：状态管理、信息层级与布局、感知性能、渐进披露、错误恢复与降级、授权的交互设计。

感知性能那一条大概最直观。流式输出就是骨架屏，用户等的不是结果，是「它在动」这件事。渐进披露也一样，agent 现在把一切一股脑倒在屏幕上，好的界面会分层：先摘要，再展开，最后才是细节。授权的交互设计则直接对应 4.3 那个失败模式，什么时候该问、问几次、默认给什么，前端的经验都是现成的。

不用带的：DOM 和 BOM 的 API、CSS 的具体属性、某个框架的 API、浏览器兼容性矩阵。

**你积累的不是浏览器知识，是怎么让一个人和一个不完美的系统共处的经验。** 这句话我觉得比任何一条具体技能都值钱。

## 八、这个类比会在哪里失效

类比的价值在于复用解法，不在于证明两者相等。有几处它一定会断，我认为必须写出来。

第一，前端的渲染是确定性的，agent 不是。同一个状态、同一份 props，React 一定给你同一棵树；同样的上下文、同样的工具，agent 可能给你完全不同的结果。前端那套可预测性的保证，纯函数、幂等、可重放，agent 一个都没有。第三节那张表，右列的机制都建立在一个前端有、agent 没有的地基上。

第二，坏结果的代价不同。前端出 bug，最坏是体验下降、白屏、用户骂两句；agent 出 bug，是它删了一个不该删的目录、发了一封不该发的邮件。这不是程度差异，是性质差异。所以三条同构里沙箱那一条最重要，也是唯一一条不能「以后再补」的。

第三，两边的用户要做的事相反。前端的用户在用界面，设计目标是降低认知负担，让他不用想；agent 的用户在审查决策，设计目标是在关键的地方提高认知负担，让他必须看见。把前端的顺滑直接搬到审批界面上，就是把人推向无脑点同意。

## 结语

把全文收一下，方便回看：

| 问题 | 我的答案 |
|---|---|
| agent 算前端吗 | 算。按「人和机器之间那一层」来划，它是人机交互的第三种范式 |
| 凭什么这么说 | 六个结构要素逐条命中，三条有源码和实测支撑 |
| 最要紧的一条同构 | 沙箱。它站在 GUI 里 undo 的位置，可逆性只是换了载体 |
| 最实用的结论 | 状态管理、信息层级、感知性能、错误恢复这些经验可以整包搬走 |
| 什么时候不成立 | 渲染不确定、坏结果代价高、两边用户要做的事相反 |

前端这二十年真正沉淀下来的，不是某个框架的 API，是一整套经验：当不确定的输入、受限的运行时和真实的人类这三件事凑到一起时，程序该怎么设计。组件怎么切、状态放哪、失败怎么降级、什么时候必须让人介入，这些答案不会因为技术栈换代而失效。

agent 把这三件事又凑了一次。所以我不觉得它是前端的替代品。**它是前端的下一个渲染目标。**

## 彩蛋

4.1 那段实测，是我把那个仓库的压缩模块单独拎出来跑的。跑之前我以为会看到一段摘要，结果只看到一句固定文本的占位。

同一天我顺手看了它的 `main.py`，欢迎横幅是用原始 ANSI 转义拼的：

```python
CSI = "\x1b["
def fg_256(n): return f"{CSI}38;5;{n}m"
```

这和《Terminal UI》里讲的是同一件事。那篇讲 Ink 怎么把 React 渲染成 ANSI 序列，这篇讲 agent 怎么在终端里调度工具，中间隔了半年，落到同一个 `\x1b[`。**前端的介质一直在变，接口层反而很稳。**
