如果你是一个前端或者客户端工程师，这两年大概不太踏实。State of Web Dev AI 2026 里有个数字，放在这个语境下读有点扎眼：问到「你用 AI 生成哪一类代码」时，排第二的答案是前端组件，4434 次提及，CSS 代码也有 3460 次。AI 正在大量做的，恰好是我们最日常的那部分工作。

这篇文章想给一个我认为站得住的答案：agent 是一种新的前端应用。文章里有一份带证据的对照表、三段我自己跑出来的实测、一个已经存在的 agent 前端，以及五个我认为是留给客户端工程师的具体位置。

## 一、人机交互的第三次范式

几年前有人问我怎么看「前端已死」这个论调。我当时的回答是：

> 行业可能会有周期，但是我以为人机交互甚至交互这个根本性领域还会存在相当长时间。聚焦这个领域，而不限于单个技术栈，可能会是一个技术常青的做一番事业的有效路径。

当时写得其实挺顺手，现在回头看，这是个挺重的判断。如果把「前端」理解成浏览器里的那点东西，那它确实可能死；如果理解成人和机器之间的那一层，那它不但不会死，还会不断长出新东西。

我在一次分享里把这个观点展开过：命令行、图形界面、语音、手势、通知、终端里的字符网格，都该算在前端的范畴里。

理由是它们回答同一个问题。一个不完美的系统，怎么把自己的状态变成人能理解和接受的呈现，同时接住人的意图。按这个划法，把自己锁死在某个终端介质里，大概是自我设限。

拿同一把尺子量 agent，它是什么就没什么悬念了：它当然是一种人机交互形态。真正值得追问的不是「算不算」，而是「它是哪一种」。

把交互史排一排，大致是这样（Shneiderman 的直接操作理论发表于 1983 年，其余时间点为本文归纳）：

| | 指令式 | 直接操作 | 意图式 |
|---|---|---|---|
| 起点 | 1960 年代终端 | 1983 年，Shneiderman | 2020 年代，agent |
| 人在做什么 | 学会机器的语言 | 操作对象本身 | 表达目标，审查结果 |
| 可见的对象 | 命令语法 | 对象与状态 | 决策与影响 |
| 出错怎么办 | 重新输入 | Undo，代价接近零 | 沙箱、审批、快照 |
| 设计目标 | 降低记忆负担 | 降低认知负担 | 在关键处提高认知负担 |

按这张表看，最要紧的是第三行。可见的对象从「对象」挪到了「决策」，后面两行就跟着变了。GUI 敢让人随便点，是因为 undo 让错误接近免费。**agent 的错误不免费，删掉就是删掉，所以它必须拿别的东西兜底。** 兜底的是什么，4.3 节回答。

## 二、领地和造法是两个问题

上面这套划法回答的是「这属于谁的领地」。它实话说还算不上工程答案，因为说不出明天该做什么。要把它变成能动手的东西，得回答第二个问题：这类程序到底由什么构成。

我习惯用六个要素来定义前端应用，它们跟技术栈无关：

1. 跑在一个自己无法控制的运行时里
2. 持有状态，并在状态变化时重新呈现
3. 通过协议与远端通信
4. 运行在一个能力受限的沙箱里
5. 面向一个会给出不确定输入的人类
6. 因此必须容错、降级、可取消

这六条不专属于前端，但凑在一起，刻画的的确是一类程序。浏览器是这类程序最成功的实例，而它 1995 年的时候，只是个文档查看器。

## 四、三条不是巧合的同构

这一节引用两个公开仓库，都是教学性质的：[build-your-claude-code-from-scratch](https://github.com/woodx9/build-your-claude-code-from-scratch)（从零手写一个 Claude Code，187 stars）和 [how-pi-agent-works](https://github.com/cellinlab/how-pi-agent-works)（讲 Pi 的原理与实现，930 stars）。前一个足够小，小到能把机制看穿；后一个跟着真实 Pi 的源码走，回答"生产环境为什么更麻烦"。

先交代一句：它们其实都是教学实现，定位是讲清楚原理。下面的讨论都冲着"这类结构容易犯什么错"，不是冲着作者。另外，两个仓库的答案确实不一样，所以批评是分开说的。

### 4.1 上下文窗口就是内存

内存有限，所以要分配、要回收、要处理碎片。上下文窗口一模一样。

前一个仓库的 `chapter5_smart_context/src/core/history/history_manager.py` 里，触发回收的条件是一行很直白的算术：

```python
def _requires_compression(self) -> bool:
    if self._compress_threshold and self.history_token_usage:
        current_usage = self.history_token_usage[-1]
        return current_usage.total_tokens > self._compress_threshold * self._model_max_tokens
    return False
```

默认 `compress_threshold` 是 0.8。用到窗口的 80% 就开始回收。这就是 GC 的触发阈值，只不过名字倒是叫 compression。

那它回收掉什么？这的确是我最想亲手看一眼的地方，所以我把这段逻辑真的跑了一遍。

```
压缩前：消息数 = 8
      角色序列 = system, user, assistant, tool, assistant, tool, assistant, user
      total_tokens=4000 时占用 97.7%，触发压缩

压缩后：消息数 = 3
      system   | You are a helpful assistant.
      user     | [Previous conversation history has been compressed to save context window space]
      user     | 顺便把 lint 也修了
```

8 条变成 3 条，中间那 5 条 assistant 和 tool 消息全部消失。消失的东西里有什么？有"我先看一下测试文件"、"找到问题了，在 src/parser.ts 第 42 行"、"应用补丁完成"。也就是说，**这一轮任务的过程记录被整段丢掉了，换来的只是一句固定的占位文本，没有任何摘要。**

这大概就是"有损"两个字的实际含义。垃圾回收至少还有个客观标准，没人引用了就是垃圾。压缩没有这个标准，丢什么全看策略写在哪一行。

也正因为没有标准，这类代码必须靠不变量来守。同一个文件里有一句注释，写得很清楚：

```python
# mustn't crop the latest user input message
```

实现里也确实在守它：先倒着找出最新一条 user 消息的下标，再用它算出两个方向各自允许裁多少。我把四种组合都跑了一遍：

| 操作 | 返回 | 结果 |
|---|---|---|
| `crop TOP 3` | Crop message successful | 8 条剩 6 条 |
| `crop BOTTOM 1` | Cannot crop: can't crop the latest user message | 保持不变 |
| `crop BOTTOM 2` | Cannot crop: can't crop the latest user message | 保持不变 |

BOTTOM 方向守住了。有意思的是 TOP 方向：按参数说明，`crop_amount` 是"要移除的消息条数"，但裁 3 条实际只少了 2 条。原因在这一行。裁剪结果里把 system 消息又拼了回去，而它们本来就在被裁掉的前缀里：

```python
system_messages = [msg for msg in current_messages if msg['role'] == Role.SYSTEM]
cropped_messages = system_messages + current_messages[crop_amount:]
```

我其实没去提 issue，也没法确定这是笔误还是有意为之，所以大概只能按"未验证"记着。但它恰好说明了一件事：**有损回收的全部危险性集中在这类算术里。** 它不会报错，不会崩，只是安静地少留一条或多留一条。前端做列表 diff 时踩过一模一样的坑。

不过"丢什么"这件事，还有另一种答案。

后一个仓库讲的是真实 Pi 的压缩链路，它给的三个不变量和上面几乎相反：原始历史不删除，后续上下文由 summary 加最近消息重新拼出来，而且 summary 不是孤立文本，它带着恢复指针。一条压缩记录长这样：

```json
{"type":"compaction","id":"c1","parentId":"a1","summary":"前面已经定位到...","firstKeptEntryId":"u8"}
```

`firstKeptEntryId` 是关键。它回答"后续原文从哪条接回来"。没有它，重建上下文时要么重复消息，要么漏消息。触发条件也不是消息条数，而是预算：

```ts
contextTokens > contextWindow - reserveTokens
```

Pi 当前默认 `reserveTokens` 是 16384，`keepRecentTokens` 是 20000。前者回答"要给模型回复留多少空间"，后者回答"最近多少 token 必须保留原文"。这两个数字本身就是设计结论：压缩不是把窗口填满再处理，是给下一次输出预留位置。

更有意思的是，那份仓库把「上下文压缩只做删除」直接写进了常见错误清单，症状是"长会话能继续，但模型忘了之前的关键决策"，修正是"用摘要替换旧消息，并保留最近消息原文"。

于是同一个内存回收问题，两个实现给了两种答案：

| | 就地删除 | 追加摘要 entry |
|---|---|---|
| 动作 | 修改消息数组 | 往日志追加一条记录 |
| 原文 | 丢掉 | 保留，可审计可重建 |
| 恢复点 | 没有 | `firstKeptEntryId` |
| 前端里的对应物 | 可变状态，手动清理 | append-only 日志加快照 |

右列那个词前端工程师很熟。它就是 event sourcing，是 Redux DevTools 里那个时间旅行：把变化存成数据，于是回到过去只是一次指针操作。前作里写 Pi"把一切做成数据"，说的就是这件事。

还有一处细节值得记下来。Pi 的切分点有硬规则，可以在用户消息、assistant 消息、自定义消息处切，但不会切在工具结果上。因为一次工具调用不是一个点，而是"发出调用、执行、读回结果"这三步。切在中间，模型会看到一个没有来源的结果，或者一个没有结果的调用。

这不就是事务边界吗？前端做批量更新时也有同样的约束：一个原子操作不能被拆进两次渲染，否则中间态会被看见。

### 4.2 工具调用就是 API 契约

一个有工具能力的 agent，本质上是在调用一批它看不见实现的接口。描述这些接口的东西是一份 JSON Schema。这就是 propTypes，是 TypeScript 类型声明，是 OpenAPI 文档，责任完全一样：在调用发生之前把契约说清楚。

前一个仓库的 chapter1 倒是给了两份对照实现，同一件事两种写法，放一起看特别清楚。

第一份是原生函数调用：工具用 JSON Schema 声明，模型返回结构化的 `tool_calls`，宿主直接 `json.loads` 拿参数。

```python
tools = [{
    "type": "function",
    "function": {
        "name": "search_gutenberg_books",
        "description": "Search for books in the Project Gutenberg library",
        "parameters": {
            "type": "object",
            "properties": {
                "search_terms": {
                    "type": "array",
                    "items": {"type": "string"},
                    "description": "List of search terms to find books"
                }
            },
            "required": ["search_terms"]
        }
    }
}]
```

第二份把契约写成了提示词里的一段示例文本，让模型自己吐 XML，宿主再用正则去捞：

```python
xml_match = re.search(r"<search_gutenberg_books>[\s\S]*?</search_gutenberg_books>", model_text)
if not xml_match:
    raise ValueError("未找到 <search_gutenberg_books> 标签")
```

差别在哪？其实一眼就能看出来。第一份里，参数名和类型是运行时校验的；第二份里，契约是一段自然语言，而校验等于一句 `raise ValueError`。第一份加第二个工具是往数组里再加一项；第二份加第二个工具，得再写一个正则，而且标签名硬编码在里面。

**契约由谁保证，决定了错误在什么时候暴露。** 这不是提示词技巧，而是接口设计，和写 REST 接口时纠结参数该不该必填是同一件事。

契约的分量有多大，老实说我也没想到，所以专门量了一下。这个实现一共两个工具，我把它们的 `json_schema()` 序列化后统计字符数：

| 项 | 字符数 |
|---|---|
| `cmd_runner` 的完整 schema | 7485 |
| 其中 `description` 说明文字 | 6852 |
| `smart_context_cropper` 的完整 schema | 3668 |
| 其中 `description` 说明文字 | 2745 |
| 两个工具合计 | 11153 |
| 用户任务原文「修复这个仓库里的 bug，让 npm test 全部通过」 | 28 |

**工具定义是用户任务的 398 倍。** 这个比例不一定普适，毕竟示例里的任务特别短，但方向是对的：你写的那段工具说明，占的是和用户对话同一条预算。它不是文档，它是每次请求都要重新付一遍的上下文。

顺着看还有一处细节，其实挺典型。那个仓库的循环里有这么一段：

```python
try:
    args = json.loads(tool_call.function.arguments)
except json.JSONDecodeError as e:
    self.messages.append({"role": "tool",
                          "name": tool_call.function.name,
                          "content": "tool call failed due to JSONDecodeError"})
    continue
```

参数解析失败时，它没有崩，而是把一句错误说明作为工具结果回灌给模型，让模型下轮自己改。**失败被当成数据，而不是异常。** 这就是错误边界，只是错误本身也变成了上下文里的一条消息。前端写错误边界时也是这个取舍：是抛出去让上层接，还是渲染成一个能继续操作的降级界面。

再往上走一层，MCP 的位置也清楚了。前一个仓库的 chapter8 专门写了一个 MCP 客户端。MCP 相当于工具世界的 HTTP，把「怎么描述和发现一个工具」标准化，让工具能跨 harness 复用。前端对这个套路很熟，我们就是靠一个协议把后端能力变成浏览器能用的东西。

### 4.3 沙箱就是浏览器的安全模型

这一条我倒是认为最深，也最容易被当成顺口一说。

浏览器为什么要有同源策略、要有权限弹窗？因为它的核心矛盾是：不可信的内容会进入一条能操作真实资源的执行路径。页面里的一段第三方脚本不该读你的摄像头，也不该读另一个站点的 cookie。

把「第三方脚本」换成一段从网页或工具返回里读到的文字，把「读摄像头」换成「删掉这个目录」，这就是提示词注入。

先看第一个仓库里，「沙箱」长什么样。执行命令的工具叫 `cmd_runner`，它的实现是这一行：

```python
result = subprocess.run(command, shell=True, capture_output=True, text=True, timeout=30)
```

`shell=True`，没有任何限制。那"安全"写在哪？写在工具说明里，写成了给模型看的行为规范：

```
1. Security Check:
   - Always check if the command is potentially dangerous (e.g., rm, sudo, chmod 777, format, del, etc.)
   - If the command is dangerous or could cause system damage/data loss, you MUST set need_user_approve=true
```

这段说明的确有 6852 字符，占了整个 schema 的九成。也就是说，**这个工具的安全策略，是一篇给模型读的作文。**

更值得琢磨的是审批本身。`need_user_approve` 不是宿主强加的门，它是工具的一个参数，由模型自己填：

```python
"need_user_approve": {
    "type": "boolean",
    "description": "Whether the crop messages action requires explicit user approval before execution",
    "default": True
}
```

宿主读它的时候是这样：

```python
need_user_approve = args.get('need_user_approve', False)
```

**默认值是 False。** 模型不主动要求审批，就没有审批。整条链路上没有任何东西在模型判断失误时兜底。

这其实不是我在挑刺。第二个仓库把同一件事直接写进了常见错误清单，标题是「让模型直接决定危险副作用」，症状是"模型生成了删除文件、覆盖配置、执行危险命令的调用"，修正里列了四条：路径限制、参数校验、before hook、必要的人类确认。两个独立实现，一个演示了坑，一个把坑标了出来。

这正是浏览器三十年前学到的教训。当年防 XSS 靠转义和过滤危险字符，被打败了；沙箱和同源策略才是解法。**边界不是写在说明里的规矩，而是宿主画出来的线。** 上面这套结构，等于把边界交给了模型，而模型正是那个会读到不可信内容、可能被注入的一方。

Simon Willison 讲提示词注入讲了好几年，他的判断一直是这个问题没有被解决，而且恐怕不容易被解决。

他给出的危险条件是三件事同时成立：能碰到私有数据、会读到不可信内容、有办法把数据送出去。三件事凑齐，防护就很难做。

上面这个例子恰好三件都占：能读文件、会读到命令输出、能通过网络发出去。

那正确的做法是什么？回到第一节那句话。GUI 靠 undo 兜底，agent 丢掉 undo 之后，兜底的东西只能是边界：能力最小化、默认拒绝、把危险操作放到进程外。前作里 Pi 的选择更极端，它干脆不做权限弹窗，理由是进程内的半吊子沙箱容易被误当成真正的安全边界，隔离请到操作系统或容器那一层去画。

两种做法倒是针锋相对，一个把策略写进提示词，一个把边界推到进程外，但立在同一个前提上：**信任不该放在模型这一侧。**

## 五、这套前端的零件，已经有人凑齐了

上面讲的是循环怎么转。第二个仓库里还有另一半，而且是更贴题的一半。

`how-pi-agent-works` 的 `examples/teaching-agent/src/client/App.tsx` 是一个 React 客户端，14314 字节。我把它从头读了一遍，想看看"agent 的界面"到底用了什么新东西。

答案其实是什么新东西都没有。

| 它里面的函数 | 它干的事 | 前端里管这个叫什么 |
|---|---|---|
| `applyStreamEvent(session, event)` | 收旧状态和一个事件，返回新状态 | reducer |
| `applyMessageEvent` / `replaceMessage` | 用事件增量更新消息列表 | 列表更新 |
| `appendMessageIfMissing` / `messageKey` | 按 key 决定插入还是替换 | 列表 key 与去重 |
| `buildSessionTree(entries)` | 把扁平的 entry 数组拼成树 | 扁平转树 |
| `SessionTreeNodeView` | 递归渲染这棵树 | 递归组件 |
| `MessageCard` / `ToolCallBlock` / `ToolCard` | 分别渲染消息、工具调用块、工具定义 | 组件化 |

数据通道也是最标准的那种。提交之后 `POST /api/runs` 拿到 `runId`，再开一条 SSE 收事件；每收到 `message_start`、`message_update`、`tool_execution_start` / `end`，就把事件追加到时间线，同时增量更新聊天区；收到 `run_done` 之后，用服务端返回的完整 session 覆盖本地状态，把增量过程中可能漏掉的 entry 一次对齐。

最后那一步大概是前端工程师天天在做的，叫乐观更新之后跟服务端对账。

那个仓库的前端文档里有一句话，我认为是整篇最该被引用的一句：

> 前端的任务不是"做一个聊天框"这么简单。它要把 Agent 的过程讲清楚。

它还顺带把「UI 不展示中间事件」列进了常见错误，症状写得很传神："用户只看到卡住了，不知道是在等模型还是工具"。修正办法是把那批中间事件暴露出来，让界面能解释当前状态。

所以"agent 需要一个前端"这件事，不需要我再论证了。**它已经发生了，而且是用前端最标准的那套零件搭起来的。**

## 六、Agent UI 不是 Chat UI

第五节的客户端还有一件事值得回头看。它有四种卡片：`MessageCard`、`ToolCallBlock`、`ToolCard`、`SessionTreeNodeView`。

消息只是其中之一。另外三种渲染的分别是工具调用、工具定义，以及会话树的分支关系。

这个细节其实比它看上去重要。如果 agent 的界面真是「聊天框」，那 message 应该吃掉全部，最多再添几种气泡样式。可真实实现里，消息和工具调用倒是平级的对象，各自有自己的渲染分支。

换句话说，这个界面渲染的核心对象，已经不是「谁说了什么」。

那是什么？把传统 UI 里那些熟面孔排一排，再看 agent 界面里对位的东西：

| 传统 UI | 它表达什么 | Agent UI | 它表达什么 |
|---|---|---|---|
| Button | 执行一个动作 | Action | 系统将执行一个动作 |
| Form | 提供输入 | Intent | 系统如何理解我的目标 |
| Menu | 选择选项 | Tool | 系统打算用什么手段 |
| Preview | 变更前先看一眼 | Diff | 系统准备改什么 |
| Dialog | 确认 | Approval | 系统请求我授权 |
| List | 展示结果 | Evidence | 系统凭什么这么判断 |
| Progress | 还要多久 | Trace | 它到底在干什么 |
| Undo | 撤销，代价接近零 | Rollback | 撤销，要快照和沙箱 |

左列回答的是「我要操作哪个对象」，右列回答的是「系统准备怎么实现我的意图」。

这张表里大概最要紧的是最后一行。GUI 敢让人随便点，靠的是 undo 代价接近零，点错了再点回来，整个直接操作范式的勇气都建立在这上面。

agent 界面里没有这个便宜可占。撤销一次错误的文件修改，需要快照，需要在上一步动手之前就把它拦住。代价从零变成非零，交互设计的前提的确就整个换了。

这也正是 4.3 那节里沙箱的位置：它站在 undo 原来站的地方。

再看 Diff 和 Evidence 这两行，它们有个共同点，不是给用户操作用的，是给用户判断用的。传统 UI 的 List 展示结果，看完就完事；agent 界面的 Evidence 展示依据，用户得拿它来判：这个结论靠不靠谱，要不要让它继续。

于是可以给这块新领地下一句尽量不含糊的定义：

> 传统前端把状态渲染给人看。agent 前端把决策渲染给人看，并且必须让人能约束它。

后半句不能省。渲染是被动的，约束是主动的，授权、打断、回滚、接管都算。少一样，界面就退化成一块只能看不能管的显示器，而显示器撑不起前端这个说法。

那为什么大家还是先做成了聊天框？

因为模型的输出天然是一段文本流，把它原样倒出来是成本最低的做法。聊天框是能用的下限，不是好用的上限。一直停在这个下限会怎样，那个仓库的常见错误清单里有个挺传神的症状：**「用户只看到卡住了，不知道是在等模型还是工具」。**

一个聊天框没有能力表达「正在执行第三个工具调用」，也没有能力表达「这条命令需要你批准」。这些不是聊天的内容，是系统的状态。

这套新原语其实还没有名字。没有公认的分类，没有组件库，没有设计规范，连「一个 agent 界面该长什么样」都还在各家自己摸索。有原语要定义、有分类要拆、有规范要立，这本身就是机会，第九节那五个位置，很大一部分就长在这里。

## 七、这条路的尽头

第五节那个客户端回答了"现在长什么样"。接下来这个问题是"下一步缺什么"。

不妨回头看浏览器怎么从文档查看器变成应用平台，靠的是三件事。状态，也就是 JS 加 DOM，页面第一次能记住东西。协议，也就是 XHR 和 fetch，页面第一次能带着数据自己更新。能力，也就是权限模型，页面终于能碰摄像头、文件和通知，还不至于出事。

把这三件事的 agent 版本排出来：状态是会话树和上下文管理，协议是 MCP，能力是工具审批和沙箱。已经全在了。

那再往下会缺什么？我猜缺的全是前端已经有的东西：组件化、布局、状态管理、设计系统、DevTools。这几个词听着像是空泛的愿望，但第九节会把它们一个个拆成具体的活。

这一串预测如果成立，结论就有点意思了：**缺口全在「怎么让人看见」这件事上。** 模型能力的进步不解决它，因为这是呈现和交互的问题，不是推理的问题。

## 八、顺带纠偏：窗口开到一百万，就不用管上下文了？

这是我最近听到最多的一句。既然窗口都到一百万 token 了，上下文管理是不是可以不做了。

按 4.1 那段代码看，这个说法站不住。窗口变大无非相当于内存变便宜，内存变便宜从来没有让 GC 消失过。何况中间信息不敏感的问题不随窗口增长而缓解，反而更明显，东西越多越容易淹。

数据也不支持。同一份调查里问「最希望 AI 补上什么能力」，长期记忆排第二，占 16.0%，仅次于真实性的 17.3%；大代码库支持 6.2%，运行时行为感知 8.3%。至于痛点那一栏，缺上下文排第三，占 14.2%，前面是幻觉和生成代码质量差。这些选项拼起来说的是同一句话：它记不住，也看不到足够多的东西。

窗口解决的是容量，压缩解决的是预算和取舍。这的确是两件事，别混。

## 九、这条赛道上有五个位置

前面七节讲的是「这是同一个领域」。但知道是同一个领域，解决不了焦虑。焦虑的解药得是具体的：大家到底在做什么活，这些活又为什么落在你身上。

下面五个位置其实都不是我的设想，而是我在那两个真实仓库里看到有人在做的模块。

### 8.1 呈现层：把 agent 的过程讲清楚

agent 现在最大的体验问题不是答案错，是过程不可见。那个仓库把「UI 不展示中间事件」写进了常见错误，症状是「用户只看到卡住了，不知道是在等模型还是工具」。

这块活包括事件时间线、会话树、工具调用卡片、diff 审查视图、审批交互、中断与恢复。第五节那个 `App.tsx` 就是它的最小版本。

为什么是你：这些活的本质是「把复杂状态讲清楚」。信息层级怎么分、什么时候该折叠、什么该并排对比，是前端每天都在做的判断，也恰好是模型不擅长、也不关心的那一类判断。

### 8.2 状态层：会话、分支与压缩

agent 的上下文管理，本质是一套状态管理。Pi 的会话是一个 JSONL 文件，每条记录带 `id` 和 `parentId`，于是同一个文件里能原地分支；压缩不改历史，而是追加一条带 `firstKeptEntryId` 的记录。

4.1 节那两种做法的分野，前端一眼就能认出来：左边是可变状态加手动清理，右边是 append-only 日志加快照。

为什么是你：右边那套就是不可变状态加时间旅行调试。会话树是一个可以点击切换的分支结构，这在前端的 DevTools、编辑器、版本对比里都是熟题。让一个后端工程师从零建立「时间旅行」的直觉，大概比让前端建立要慢。

### 8.3 边界层：能力、权限与审批

4.3 节那个例子最能说明这块活的价值：一个能执行任意命令的工具，它的「安全」是 6852 字符的自然语言说明，而审批开关默认是关的。

浏览器是怎么解决同一个问题的？能力最小化、同源策略、用户中介授权。而且方向从来不是问得更频繁，是让安全的默认值不必问。

为什么是你：这套东西浏览器工程师做了三十年，还是被真实攻击打磨过的。现在 agent 领域最缺的恰好是这份经验，缺到需要另一个仓库专门写一条错误清单来提醒大家。

### 8.4 协议层：工具契约与适配

工具定义就是接口契约，4.2 节量出的那个 398 倍说明它占的是实打实的预算。同一份实现里还有两种写法的对照：JSON Schema 是运行时能校验的契约，而「让模型吐 XML、宿主用正则捞」等于把校验写成一句 `raise ValueError`。

MCP 的位置倒是也在这里。它相当于工具世界的 HTTP，而写一个 MCP 服务、做一层协议适配，全是接口设计的活。

为什么是你：写 schema、写接口文档、处理协议差异，这些是前端和全栈的日常。你可能三个月里就写过十个 REST 接口，而这份手感正是当前工具生态缺的。

### 8.5 观测与评测层：trace 与 eval

agent 出错的时候，最需要的的确是一份能回放的过程记录。那个仓库把中间事件暴露出来让界面能解释当前状态，这已经是 trace 的雏形。

再往上走大概是 eval。前端的测试金字塔是单元、集成、E2E，agent 的评测同样要分层：单轮工具调用对不对、多轮任务完不完成、端到端有没有副作用。

为什么是你：没有观测就没有调试，这句话前端在 2010 年代就刻进肌肉记忆了。DevTools 那种「把时间轴摊开给人看」的产品直觉，读文档补不上来。

### 8.6 收一下

| 位置 | 干的活 | 你的现成优势 |
|---|---|---|
| 呈现层 | 时间线、会话树、diff 审查、审批交互 | 把复杂状态讲清楚 |
| 状态层 | 会话存储、分支、压缩策略 | 不可变状态与时间旅行 |
| 边界层 | 权限模型、沙箱策略、审批默认值 | 浏览器三十年的安全模型 |
| 协议层 | 工具 schema、MCP、适配层 | 接口设计与协议手感 |
| 观测层 | trace、回放、eval 分层 | DevTools 与测试金字塔 |

不用带的也有清单：DOM 和 BOM 的 API、CSS 的具体属性、某个框架的 API、浏览器兼容性矩阵。这些是手艺里最表层的那一层。

**你积累的不是浏览器知识，是怎么让一个人和一个不完美的系统共处的经验。** 上面五个位置要的，都是后半句。

## 十、这个类比会在哪里失效

类比的价值在于复用解法，不在于证明两者相等。有几处它一定会断，我认为必须写出来。

第一，前端的渲染是确定性的，agent 不是。同一个状态、同一份 props，React 一定给你同一棵树；同样的上下文、同样的工具，agent 可能给你完全不同的结果。前端那套可预测性的保证，纯函数、幂等、可重放，agent 一个都没有。第三节那张表，右列的机制都建立在一个前端有、agent 没有的地基上。

第二，坏结果的代价不同。前端出 bug，最坏是体验下降、白屏、用户骂两句；agent 出 bug，是它删了一个不该删的目录、发了一封不该发的邮件。这不是程度差异，是性质差异。所以三条同构里沙箱那一条最重要，也是唯一一条不能「以后再补」的。

第三，两边的用户要做的事相反。前端的用户在用界面，设计目标是降低认知负担，让他不用想；agent 的用户在审查决策，设计目标是在关键的地方提高认知负担，让他必须看见。把前端的顺滑直接搬到审批界面上，就是把人推向无脑点同意。

## 结语

把全文收一下，方便回看：

| 问题 | 我的答案 |
|---|---|
| agent 算前端吗 | 算。按「人和机器之间那一层」来划，它是人机交互的第三种范式 |
| 凭什么这么说 | 六个结构要素逐条命中，三条有源码和实测支撑 |
| 最要紧的一条同构 | 沙箱。它站在 GUI 里 undo 的位置，可逆性只是换了载体 |
| 界面渲染的对象变了 | 从「谁说了什么」变成「系统准备做什么」，撤销从 undo 变成 rollback |
| 最实用的结论 | 呈现、状态、边界、协议、观测五个位置，都是客户端工程师的现成优势 |
| 什么时候不成立 | 渲染不确定、坏结果代价高、两边用户要做的事相反 |

前端这二十年真正沉淀下来的，不是某个框架的 API，是一整套经验：当不确定的输入、受限的运行时和真实的人类这三件事凑到一起时，程序该怎么设计。组件怎么切、状态放哪、失败怎么降级、什么时候必须让人介入，这些答案不会因为技术栈换代而失效。

agent 把这三件事又凑了一次。所以我不觉得它是前端的替代品。**它是前端的下一个渲染目标。**

最后说回开头那个焦虑。

我在《AI 时代会需要更多程序员》里用过马车到汽车的比喻，这里可以再往下推一层：当年从车夫变司机，其实很多就是同一批人。因为开车需要的判断力，车夫本来就有，路况、载重、天气、乘客，这些他每天都在判断。真正作废的是驯马和喂马那套手艺。

前端版的说法是这样。DOM 和 BOM 的 API、CSS 的具体属性、框架之间的版本差异，这些是驯马。至于状态怎么管、信息怎么分层、失败怎么降级、什么时候必须让人介入，这些是在路上判断，它们不会因为介质从浏览器换成终端、再换成 agent 就失效。

所以我的建议既不是「别怕」，也不是「赶紧转行去学模型训练」。我更想说的是：**你手里有好几样东西，正好是这条新赛道现在最缺的。** 焦虑的来源是「我熟悉的东西在贬值」，但贬值的是最表层那一片。

至于需求总量，我仍然持前作里的判断：生产力提升会长出更多场景，而不是更少的岗位。这句话我暂时只能给方向，验证不了，但它至少不是一句安慰。

## 彩蛋

4.1 那段实测，是我把那个仓库的压缩模块单独拎出来跑的。跑之前我以为会看到一段摘要，结果只看到一句固定文本的占位。

同一天我顺手看了它的 `main.py`，欢迎横幅是用原始 ANSI 转义拼的：

```python
CSI = "\x1b["
def fg_256(n): return f"{CSI}38;5;{n}m"
```

这和《Terminal UI》里讲的是同一件事。那篇讲 Ink 怎么把 React 渲染成 ANSI 序列，这篇讲 agent 怎么在终端里调度工具，中间隔了半年，落到同一个 `\x1b[`。**前端的介质一直在变，接口层反而很稳。**
